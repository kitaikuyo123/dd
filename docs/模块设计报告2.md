# ZooKeeper 模块设计报告

## 1. 模块定位
`zookeeper` 模块是 MiniSQL 的分布式协调层，负责为 Master 选主、RegionServer 注册与发现、分布式锁以及系统路径初始化提供统一封装。它基于 Apache Curator 框架封装 ZooKeeper 原生 API，向上层模块（`master`、`regionserver`）提供简洁的门面接口。

当前核心职责包括：

+ 封装 CuratorFramework，提供持久/临时/顺序节点的创建、读取、删除和监听。
+ 引导系统路径（PathBootstrapper），确保 ZooKeeper 目录结构在首次使用前就绪。
+ 基于 Curator LeaderLatch 实现 Master 节点的自动选主。
+ 持续监听 Master leader 节点变化，通知上层重连。
+ RegionServer 临时节点注册与健康感知（session 过期自动摘除）。
+ 基于 InterProcessMutex 的分布式互斥锁。
+ 手写 JSON 序列化，避免引入第三方 JSON 库。

## 2. 模块依赖
`zookeeper/pom.xml` 中主要依赖如下：

| 依赖 | 作用 |
| --- | --- |
| `common` | 使用 `Constants` 中的 ZK 路径常量和 `ServerId` 模型 |
| `curator-framework` | Curator 核心 API |
| `curator-recipes` | LeaderLatch、InterProcessMutex、CuratorCache 等高级模式 |
| `zookeeper` | ZooKeeper 原生客户端（Curator 底层依赖） |

## 5. ZkClient 设计
`ZkClient` 构造时创建 `CuratorFrameworkFactory` 实例，配置如下：

+ 会话超时：`30000ms`
+ 连接超时：`10000ms`
+ 重试策略：`ExponentialBackoffRetry`，初始 `1000ms`，最多 3 次

提供的节点操作：

| 方法 | 说明 |
| --- | --- |
| `createPersistent(path, data)` | 创建持久节点（含父节点自动创建） |
| `createEphemeral(path, data)` | 创建临时节点（session 断开自动删除） |
| `createEphemeralSequential(path, data)` | 创建临时顺序节点 |
| `delete(path)` | 删除节点及其子节点 |
| `exists(path)` | 检查节点是否存在 |
| `getData / setData` | 读写节点数据 |
| `getChildren(path)` | 获取子节点列表 |
| `watchNode / watchChildren` | 注册一次性数据/子节点监听器 |

Watcher 策略说明：`watchNode` 和 `watchChildren` 注册的是一次性监听器，触发后不会自动重新注册。对于需要持续监听的场景（如 leader 监控），使用 `CuratorCache`。

## 6. ZkManager 门面设计
`ZkManager` 组合所有子组件，是其他模块使用 ZooKeeper 功能的入口。

启动流程：`start()` → 启动 ZkClient → 引导路径。

关闭流程：`close()` 按序关闭 leaderNodeWatcher、leaderElectionService、regionServerRegistry、zkClient，异常通过 `addSuppressed` 累积。

委托方法：

| 方法 | 委托对象 |
| --- | --- |
| `participateMasterElection()` | `LeaderElectionService.start()` |
| `publishLeader()` | `LeaderElectionService.publishLeader()` |
| `watchLeader()` | `LeaderNodeWatcher.start()` |
| `registerRegionServer()` | `RegionServerRegistry.registerSelf()` |
| `watchRegionServers()` | `RegionServerRegistry.watch()` |

观察者模式：通过 `ServerListener` 接口向外部通知集群事件，包括 leadership 变化、leader 地址变化、RS 节点增删。

## 7. 选主与监听设计
### 7.1 LeaderElectionService
基于 Curator `LeaderLatch` 实现。参与者在 `ZK_MASTER_ELECTION_PATH` 下创建临时顺序节点，序号最小者成为 leader。

成为 leader 后的回调流程：
1. 设置 `leader = true`
2. 调用 `publishLeader()` 将 `ServerId` 编码为 JSON 写入 `ZK_MASTER_LEADER_PATH`
3. 通知 `LeadershipListener`

失去 leader 后设置 `leader = false` 并通知监听器。

### 7.2 LeaderNodeWatcher
使用 `CuratorCache` 在 `ZK_MASTER_LEADER_PATH` 上建立持久缓存。当 leader 节点数据变更或创建时，解码新的 leader 地址并通过 `Consumer<String>` 回调通知上层。启动时会立即读取当前值并触发回调。

与 ZkClient 一次性 Watcher 的区别：`CuratorCache` 自动重建 Watcher，适合需要持续感知的场景。

## 8. RegionServer 注册设计
`RegionServerRegistry` 提供服务注册与发现能力。

注册流程：在 `ZK_REGIONSERVERS_PATH` 下创建以 `instanceName` 命名的临时节点。节点数据包含 RS 的 gRPC 地址、MySQL 配置和启动时间。如果节点已存在则先删除再重建（处理重启场景）。

发现流程：使用 `CuratorCache` 监听 `ZK_REGIONSERVERS_PATH` 的子节点变化，通过 `forCreates` 和 `forDeletes` 回调通知 RS 节点的上线和下线。

临时节点保证：当 RS 进程崩溃或与 ZK 的 session 断开时，节点自动删除，实现自动摘除。

## 9. 分布式锁设计
`DistributedLock` 是 `InterProcessMutex` 的简单委托封装，提供：

+ `acquire()` — 阻塞获取锁
+ `acquire(timeout, unit)` — 带超时的获取尝试
+ `release()` — 释放锁
+ `isAcquiredInThisProcess()` — 检查当前进程是否持有锁

内部使用 ZooKeeper 临时顺序节点和 Watcher 实现公平可重入分布式锁。

## 10. 路径引导与序列化
### 10.1 PathBootstrapper
幂等创建系统所需的 ZK 持久路径：

| 路径 | 用途 |
| --- | --- |
| `/minisql` | 系统根路径 |
| `/minisql/masters` | Master 节点元数据 |
| `/minisql/masters/election` | 选主临时节点 |
| `/minisql/regionservers` | RS 注册节点 |
| `/minisql/tables` | 表元数据 |
| `/minisql/locks` | 通用分布式锁 |
| `/minisql/locks/tables` | 表级锁 |
| `/minisql/locks/regions` | Region 级锁 |

每个路径在创建前检查 `exists()`，确保幂等安全。

### 10.2 ZkPayloads
手写 JSON 编解码工具，避免引入 Gson/Jackson。编码方法将 `ServerId` 序列化为 `{"host":"...","port":...}` 格式；解码方法通过 `indexOf` 搜索字段名解析字符串和整数，并支持反斜杠和引号转义。

# Master 模块设计报告

## 1. 模块定位
`master` 模块是 MiniSQL 集群的大脑，负责元数据管理、集群状态维护、负载均衡、Region 分裂/合并/迁移、热点检测、故障转移、副本生命周期管理和监控服务。它通过 gRPC 接收 RegionServer 的心跳和状态上报，通过 ZooKeeper 持久化元数据，通过 gRPC 向 RegionServer 下发管理命令。

当前核心职责包括：

+ RegionServer 注册、心跳处理和状态追踪。
+ 表和 Region 元数据管理（创建/删除表、Region 注册、路由查找）。
+ 基于 Region 负载的自动均衡（随机、轮询、负载感知三种策略）。
+ Region 自动分裂（超阈值触发）和自动合并（小 Region 合并）。
+ Region 迁移（完整的状态机：开目标 → 同步 → 提升 → 关源）。
+ 热点检测与缓解（增加读副本或触发分裂）。
+ Primary 故障自动转移（Fencing Token 防脑裂）。
+ 副本恢复与全量同步协调。
+ 数据损坏修复。
+ 内置监控 Web 服务（HTTP API + SSE 实时推送）。

## 2. 模块依赖

## 4. 状态管理层

### 4.1 MetadataManager
`MetadataManager` 是元数据的唯一真相来源，所有表 schema 和 Region 拓扑持久化到 ZooKeeper。

ZooKeeper 路径设计：

| 路径 | 内容 |
| --- | --- |
| `/minisql/tables/{table}/schema` | 表 schema（protobuf `TableSchema`） |
| `/minisql/tables/{table}/regions/{regionId}` | Region 元数据（管道分隔文本，key 经 Base64 编码） |
| `/minisql/tables/{table}/regions/{regionId}/primary` | Primary 地址 `host:port` |
| `/minisql/tables/{table}/regions/{regionId}/replicas` | 副本列表（逗号分隔 `host:port`） |
| `/minisql/tables/{table}/next-id` | Region ID 自增序列 |

启动时从 ZK 加载全部元数据到内存 `ConcurrentHashMap`。关键方法包括 `createTable()`、`deleteTable()`、`registerRegionForTable()`、`removeRegion()`、`findRegion(tableName, rowKey)`（二分查找路由）和 `allocateRegionId()`。

### 4.2 ClusterManager
`ClusterManager` 维护集群运行时状态，包括活跃 RegionServer 列表、服务器负载、硬件指标、Fencing Token 和副本序列号。

核心内部类：

+ `ServerInfo` — 每个 RS 的运行时状态：最近心跳时间、Region 负载 Map、服务器指标。
+ `RegionLoad` — 每 Region 负载指标：读写请求数、存储文件大小、MemStore 大小。
+ `ServerMetrics` — 硬件指标：CPU、内存、磁盘使用。
+ `GraveyardEntry` — 已下线 RS 记录（5 分钟 TTL），用于监控面板展示。

注意：ClusterManager 不直接存储 Region 拓扑信息（Primary/副本列表），而是通过 `MetadataManager.getRegion()` 委托查询。

### 4.3 ReplicaMonitor
`ReplicaMonitor` 跟踪副本运行时健康数据（心跳、复制延迟、状态），拓扑信息来自 MetadataManager 的 Region 模型。

回调接口 `FailoverCallback` 提供三个事件：
+ `onReplicaFailed` — 副本故障（触发 FailoverCoordinator）
+ `onReplicaLagging` — 副本延迟超过阈值（默认 10 秒）
+ `onReplicaRecovered` — 副本恢复在线（触发 RecoveryCoordinator）

延迟检测：`updateHeartbeat()` 发现复制延迟超过阈值时，将副本标记为 LAGGING 并触发回调。

### 4.4 ReplicaLifecycleManager
`ReplicaLifecycleManager` 追踪每个副本在所有编排流程中的生命周期状态，提供统一审计轨迹。

生命周期状态：`BOOTSTRAPPING` → `CATCHING_UP` → `SECONDARY_READY` → `FINALIZING` → `PROMOTING` → `PRIMARY_READY`；异常状态：`LAGGING`、`OFFLINE`、`REBUILDING`、`REMOVED`、`FAILED`。

关键能力：`whenReady(regionId, serverId)` 返回 `CompletableFuture`，在副本达到 SECONDARY_READY 时完成；`awaitReplicasReady()` 在超时内等待指定副本就绪。用于建表时确保副本就绪后才返回成功。

## 5. 负载均衡与 Region 管理层

### 5.1 LoadBalancer
支持三种均衡策略：`RANDOM`、`ROUND_ROBIN`、`LOAD_BASED`（默认）。

LOAD_BASED 策略评分规则：
+ 每个 Primary Region 加 10 分
+ 过载阈值：分数超过 70 的服务器不再分配新 Region
+ 选择最低负载的候选服务器，减去热点惩罚

`HotSpotRegistry` 记录热点 Region 与表的映射，对已托管同表热点 Region 的服务器施加惩罚，避免热点集中。

`computeBalanceActions()` 每轮最多生成一个迁移动作，并考虑正在进行的迁移数量。

### 5.2 RegionSplitCoordinator
监控 Region 大小，超过分裂阈值时自动触发分裂。

分裂工作流：
1. 通过 gRPC 从托管 RS 获取分裂点（中位数采样）
2. 分配两个新 RegionId
3. 指示 RS 执行物理分裂
4. 更新元数据（删除旧 Region，注册两个新 Region）
5. 可选地将右侧 Region 迁移到其他服务器
6. 为两个子 Region 确保副本拓扑
7. 通知 RegionMergeCoordinator 记录新鲜分裂（合并冷却期）

分裂点选择：采样最多 4096 个不同 rowKey，排序后取中位数；采样不足时回退到字节级中点计算。

### 5.3 RegionMergeCoordinator
定期检查相邻小 Region 是否应该合并。

合并条件：相邻（左 Region 的 endKey == 右 Region 的 startKey）、同服务器、总大小不超过最大合并大小、未在冷却期内。

合并工作流：获取两个 Region 的分布式锁（按排序顺序避免死锁）→ 重新验证条件 → 指示 RS 物理合并 → 更新元数据 → 确保副本拓扑。

`forceMerge(tableName)` 可绕过大小检查和冷却期，先通过 RegionMigrationCoordinator 将 Region 共置再合并。

### 5.4 RegionMigrationCoordinator
管理 Region 从一个 RS 迁移到另一个 RS 的完整生命周期。

迁移状态机：

```
OPENING_TARGET → INITIAL_SYNC → FINALIZING_SOURCE → WAITING_FINAL_SYNC →
PROMOTING_TARGET → CLOSING_SOURCE → COMMITTING_METADATA → COMPLETED
```

关键步骤：
1. 在目标 RS 上打开 Region
2. 在源 RS 上启动迁移（写入继续，捕获当前序列号）
3. 等待初始复制追赶
4. 在源 RS 上终止迁移（阻塞写入，排空 WAL）
5. 等待最终同步
6. 提升目标为 Primary（带 Fencing Token）
7. 关闭源 Region
8. 提交元数据切换

失败回滚：在目标提升前，中止源的迁移并关闭目标；目标提升后需要人工干预。

### 5.5 HotSpotCoordinator
通过收集心跳中的 Region 负载快照，计算时间标准化的 QPS 增量来检测读写热点。

热点分类：`READ`、`WRITE`、`MIXED`。

缓解动作：
+ 读热点：`ADD_READ_REPLICA`（在最低负载服务器上添加副本）
+ 写热点：`SPLIT_REGION`（委托 RegionSplitCoordinator）

冷却机制防止同一 Region 被重复触发。

### 5.6 RebalanceSupport
`RebalanceSupport` 是 split/merge/migration 三个协调器共享的工具类，避免逻辑重复。

主要方法：
+ `ensureReplicaTopology(regionId)` — 选择服务器以满足目标副本数，注册元数据并通过 RecoveryCoordinator 引导新副本
+ `selectServersForReplication()` — 使用 LoadBalancer 挑选服务器
+ `cleanupRegionRuntime()` — 从 ClusterManager、ReplicaMonitor 等清理 Region
+ `acquireRegionLock() / releaseLock()` — 通过 ZK 获取/释放分布式锁

## 6. 故障恢复层

### 6.1 FailoverCoordinator
处理 Primary 副本故障时的自动故障转移。

关键特性：
+ 选择最健康且延迟最低的 Secondary 提升为 Primary
+ 指数退避冷却：每次失败尝试将冷却时间翻倍
+ 紧急故障转移模式：绕过冷却和重试限制
+ 手动故障转移：指定目标服务器的维护操作
+ Fencing Token：要求单调递增的 token 才能执行提升，防止脑裂

故障转移工作流：获取分布式锁 → 选择新 Primary（健康活跃副本中延迟最低者） → 验证候选副本已追赶 → 通过 gRPC 提升 → 更新元数据（MetadataManager、ClusterManager、ZK） → 记录事件。

### 6.2 RecoveryCoordinator
编排新副本引导和故障副本恢复的完整生命周期。

恢复工作流（`performRecovery`）：
1. 转换生命周期为 BOOTSTRAPPING 或 REBUILDING
2. 在目标 RS 上打开 Region
3. 注册副本到元数据和 ReplicaMonitor
4. 执行复制追赶（全量同步或增量同步）
5. 标记副本为 SECONDARY_READY
6. 执行副本目标数检查（裁剪多余副本）

服务器协调（`reconcileRecoveredServer`）：当 RS 重新上线时，遍历所有 Region，重开 Primary Region，恢复已有副本，引导新副本以满足目标副本数。使用去重机制防止多服务器并发注册时的重复调度。

### 6.3 DataRepairCoordinator
协调数据损坏修复。发现损坏服务器后，找到最健康副本（最高序列号），若损坏的是 Primary 则先触发故障转移，然后从健康副本发起全量同步到损坏副本。修复异步执行，维护有界修复历史（最多 1000 条）。

## 7. RPC 服务层

### 7.1 MasterServiceImpl
实现 `MasterServiceGrpc` 的核心 RPC 端点。

主要 RPC 方法：

| 方法 | 说明 |
| --- | --- |
| `registerRegionServer` | 注册 RS，触发恢复协调 |
| `heartbeat` | 处理心跳，更新负载和指标，喂入热点检测器 |
| `reportRegionStatus` | 更新 Region 状态，CLOSED+error 触发故障恢复 |
| `getRegionLocation` | 按 table+rowKey 路由查找 |
| `createTable` | 建表含预分裂、副本放置、Region 打开、副本组创建和引导同步 |
| `deleteTable` | 关闭所有 Region，清理元数据和副本组 |
| `reportPrimaryChange` | 处理 Primary 变化通知 |

定时任务：
+ 负载均衡调度器（默认 5 分钟间隔）
+ 热点检测器（默认 10 秒间隔）
+ Region 分裂建议检查器（默认 30 秒间隔）
+ Region 合并检查器（默认 60 秒间隔）

领导权检查：所有变更 RPC 检查 `ensureLeader()`，非 leader 的 Master 以 "standby" 状态拒绝请求。

### 7.2 RegionServerCommandClient
定义 Master 到 RegionServer 的命令接口，包括 `openRegion`、`closeRegion`、`promoteToPrimary`、`getReplicationLag`、`getSplitKey`、`splitRegion`、`mergeRegion`、`startMigration`、`finalizeMigration`、`abortMigration`。

`GrpcRegionServerCommandClient` 是 gRPC 实现，通过 `GrpcChannelFactory` 复用连接，每次 RPC 使用短生命周期 `CommandSession`（带 deadline），使协调器保持传输层无关。

### 7.3 MasterMain
进程入口，编排启动序列：

1. 从配置文件加载配置（支持环境变量覆盖）
2. 初始化 ZooKeeper（可选嵌入式 ZK 用于开发模式）
3. 按依赖顺序创建所有组件：MetadataManager → ClusterManager → LoadBalancer → ReplicationCoordinator → ReplicaMonitor → ReplicaLifecycleManager → FailoverCoordinator → RecoveryCoordinator → MonitoringService → DataRepairCoordinator
4. 启动 gRPC 服务（MasterServiceImpl）
5. 启动监控 HTTP 服务（MonitorHttpServer，端口 = gRPC 端口 + 10）
6. 通过 ZkManager 参与 leader 选举
7. 注册 ZK 事件监听器（RS 节点增删触发恢复）
8. 启动配置热加载线程（每 30 秒检查文件修改，热更新负载均衡和热点设置）

关闭钩子按逆序停止所有组件。

## 8. 监控服务层

### 8.1 MonitoringService

## 1. 模块定位
`regionserver` 模块是 MiniSQL 的数据服务工作节点，负责托管 Region、处理客户端和 Master 的 gRPC 请求、管理 Region 生命周期（打开/关闭/分裂/合并）、执行读写操作、维护复制通道和定期向 Master 发送心跳。它是实际承载数据读写和存储引擎交互的核心模块。

当前核心职责包括：

+ 接收并处理客户端 Put、Get、Scan、Delete 请求。
+ 接收并执行 Master 下发的 Region 管理 RPC（Open、Close、Split、Merge）。

+ Region 分裂（采样中位数切分）和合并（相邻 Region 归并）。
+ 基于 gRPC 双向流的快照传输，支持副本全量同步和迁移。

### 4.2 RegionServer
核心运行时编排器，持有所有子组件。

`start()` 流程：
1. 设置 `running = true`
2. 启动 ReplicationCoordinator
3. 通过 gRPC 连接到 Master
4. 在配置端口启动 gRPC Server，绑定 RegionServerServiceImpl

1. 关闭 gRPC Server（30 秒排空超时，然后强制关闭）
2. Flush 所有打开的 Region
3. 停止 ReplicationCoordinator
4. 关闭所有 Region
5. 关闭 Master gRPC Channel

数据操作（`put`、`get`、`scan`、`delete`）：
+ 写入操作检查 Region 是否为 OPEN 状态且未被写阻塞（`isWriteBlocked()`）
+ 写入操作支持 `bypassWriteBlock` 标志，用于副本应用复制变更时绕过写阻塞
+ 读取和扫描直接委托给 RegionStorage

## 5. gRPC 服务实现

### RegionServerServiceImpl
实现 `RegionServerServiceGrpc` 的所有 RPC 方法，是外部请求的统一入口。

核心 RPC 方法：

| 方法 | 说明 |
| --- | --- |
| `put` | 写入数据。仅 Primary 可写。写入 WAL → 本地提交 → 同步复制到副本 → 标记 WAL 已应用 |
| `get` | 按 rowKey 点查，检查 `canServeReads()` |
| `scan` | 范围扫描，支持 WHERE、ORDER BY、LIMIT、聚合下推和谓词下推 |
| `delete` | 按 rowKey 删除 |
| `replicate` | 接收复制变更，带 CRC32 校验和序列号追踪 |
| `streamSnapshot` | 双向流式快照传输，用于副本全量同步 |
| `getSnapshot` | 服务端流式快照传输（每批 1000 KV），用于迁移 |
| `openRegion` | 打开 Region，创建存储、注册到 RegionManager、初始化副本组 |
| `closeRegion` | 关闭 Region，支持 abort 和 dropTable 标志 |
| `splitRegion` | 执行 Region 分裂，委托 RegionSplitService |
| `mergeRegion` | 执行 Region 合并，委托 RegionMergeService |
| `promoteToPrimary` | 提升副本为 Primary，更新 Fencing Token |
| `startMigration` | 开始迁移：全量同步 + 增量 WAL 追赶 |
| `finalizeMigration` | 阻塞写入，执行最终增量追赶 |
| `abortMigration` | 取消迁移，解除写阻塞 |

### 写入路径（put 详解）
1. 验证 Region 在本服务器上是 Primary
2. 将 protobuf KeyValue 转换为模型 KeyValue
3. 通过 `replicationCoordinator.logMutations()` 追加到 WAL
4. 通过 `regionServer.put()` 本地提交
5. 同步复制到副本组（尽力而为，失败降级但不拒绝客户端写入）
6. 标记 WAL 条目为已应用

### 扫描路径（scan 详解）
1. 通过 `SQLParser` 解析 WHERE 子句为 Condition AST
2. 使用 `PredicatePushdownPlanner` 提取扫描范围（startKey/endKey）和列谓词
3. 构建 `StorageScanFilter` 包含列谓词和投影列
4. 决定流式 vs 物化路径：
   + **流式**：无 ORDER BY、无聚合且 WHERE 完全下推
   + **物化**：需要排序、聚合或复杂 WHERE 后过滤
5. 物化路径：组装行 → 后过滤 → 排序 → LIMIT/OFFSET → 可选本地聚合

## 6. Region 管理

### 6.1 RegionManager
管理本服务器上所有托管 Region 的生命周期。维护 7 个并发 Map：

| Map | 内容 |
| --- | --- |
| `regions` | regionId → Region 元数据 |
| `regionStorages` | regionId → RegionStorage |
| `regionStates` | regionId → RegionState (OPENING/OPEN/CLOSING/CLOSED) |
| `regionPrimaryStatus` | regionId → 是否为 Primary |
| `lastAppliedReplicationSequenceIds` | regionId → 已应用的复制序列号 |
| `regionWriteBlocked` | regionId → 是否写阻塞 |
| `regionFencingTokens` | regionId → Fencing Token |

关键操作使用 `ConcurrentHashMap.compute()` 保证原子性。`openRegion` 创建 RegionStorage、规范化拓扑并初始化副本组；`closeRegion` 刷盘/清理后从所有 Map 中移除。

Fencing Token 机制：`verifyFencingToken()` 要求写入时提供的 token >= 当前 token，防止旧 Primary 脑裂写入。

### 6.2 RegionStorage
Region 级存储包装器，封装 `StorageEngine` 实例并提供读写计数和大小估算。

特性：
+ `readRequestCount`、`writeRequestCount` — AtomicLong 请求计数器
+ `getStoreFileSize()` — 带有 10 秒 TTL 缓存的磁盘大小估算
+ 委托 `put`、`get`、`scan`、`delete`、`flush`、`compact`、`close`、`dropData` 到底层存储引擎

## 7. Region 分裂与合并

### 7.1 RegionSplitService
处理 Region 分裂为两个相邻 Region。

分裂点选择（`findBestSplitPoint`）：
1. 蓄水池采样最多 4096 个不同 rowKey
2. 排序后选取严格位于 startKey 和 endKey 之间的中位数 key
3. 采样不足 2 个 key 时回退到字节级中点计算

分裂执行（`splitRegion`）：
1. 验证分裂点有效性
2. 阻塞父 Region 写入
3. 创建两个新 Region 元数据（左：startKey→splitKey，右：splitKey→endKey）
4. 创建两个新 RegionStorage
5. 扫描父 Region，将每个 KeyValue 写入对应的子 Region
6. 任一侧 0 条目则中止（不均衡分裂）
7. 关闭父 Region（dropTable=true）
8. 注册两个子 Region 为 OPEN

### 7.2 RegionMergeService
处理两个相邻小 Region 的合并。

合并条件（`canMerge`）：
+ 相邻（左 endKey == 右 startKey）
+ 合并后大小不超过 `MAX_MERGE_SIZE`
+ 两者均低于合并阈值，或任一低于最小合并大小

合并执行：创建合并后 Region → 迁移两侧数据 → 关闭原始 Region → 注册合并后 Region。

回滚支持：数据迁移失败时，关闭合并存储，重新打开原始 Region。若回滚本身也失败则需人工干预。

## 8. 心跳与 Master 通信

### HeartbeatSender
定期向 Master 发送心跳，携带 Region 负载和服务器指标。同时通过 ZooKeeper 发现 Master leader 地址。

启动流程：
1. 启动 ZkManager
2. 注册 `ServerListener` 监听 leader 地址变化，触发重连
3. 注册本 RS 为 ZK 临时节点
4. 向 Master 发起注册
5. 以心跳间隔调度定时任务

心跳内容：
+ ServerId 和时间戳
+ Region 负载：每 Region 的读写请求数、存储文件大小、MemStore 大小
+ 服务器指标：CPU 使用率（`OperatingSystemMXBean`）、内存使用、磁盘使用

CPU 测量：优先使用 `getProcessCpuLoad()`；不可用时回退到基于 `getProcessCpuTime()` 增量计算。

## 9. 谓词下推设计

### PredicatePushdownPlanner
将 WHERE 条件转换为存储层扫描范围和列谓词，最小化存储引擎到上层的数据传输量。

支持的下推：
+ 单主键列的等值/范围条件 → startKey/endKey 扫描范围收窄
+ AND 条件的交集合并（范围取交集，谓词取并集）
+ 非主键列的简单条件 → `StorageColumnPredicate` 列级过滤

不支持的下推（返回 `PushdownPlan.none()`）：
+ OR 条件
+ 复合主键
+ LIKE 或其他非标准运算符

`PushdownPlan` 包含 `startKey`、`endKey`（收窄的扫描范围）、`columnPredicates`（列谓词列表）、`pushdown`（是否有下推）、`fullyPushedDown`（条件是否完全下推，无需后过滤）。

### Client-RS 下推协作

Client 端不做下推资格判断，所有 WHERE 条件都以 SQL 字符串形式发送给 RS。RS 端负责全部的下推规划和执行。但 Client 端承担一项 RS 无法完成的工作：**Region 裁剪**。

每个 RS 只有自己的 Region 数据，没有全局拓扑视图。只有 Client（通过 Router）知道所有 Region 的键范围分布。因此 Client 利用 `ScanRangeAnalyzer` 从 WHERE 条件中提取主键扫描范围，与 Router 中每个 Region 的 startKey/endKey 做交集判断，跳过无关 Region，避免无用网络请求。这是 Client-RS 两层协作的互补设计：

| 层级 | 优化手段 | 粒度 | 目的 |
| --- | --- | --- | --- |
| Client（`ScanRangeAnalyzer`） | 主键范围 → Region 裁剪 | Region 粒度 | 减少网络请求 |
| RS（`PredicatePushdownPlanner`） | 主键范围 → scan 缩窄 + 列谓词 | 存储引擎粒度 | 减少磁盘 I/O |

## 4. JDBC 驱动层

### 4.1 MiniSQLDriver
JDBC Driver 入口，实现 `java.sql.Driver`。通过 Java SPI（`META-INF/services/java.sql.Driver`）自动注册到 `DriverManager`。

接受 URL 格式：`jdbc:minisql://zkhost:2181`。

`connect()` 验证 URL 后创建并返回 `MiniSQLConnection`。

### 4.2 MiniSQLConnection
核心连接对象，实现 `java.sql.Connection`。组合 ZooKeeper 发现、Master 通信、RegionServer 路由、查询执行和 DML/DDL 操作。

关键初始化流程：
1. `parseUrl()` 从 JDBC URL 提取 ZK 地址
2. `initialize()` 连接 ZooKeeper，设置 ZkClient 到 Router
3. `refreshMasterAddress()` 从 `/minisql/master/leader` 读取 Master 地址，创建 gRPC stub

查询执行（`executeQuery`）：
+ 通过 `SQLParser` 解析 SQL 为 AST
+ 委托 `ParallelQueryExecutor.executeQuery()` 返回 `List<Row>`
+ 转换为 `MiniSQLResultSet`

更新执行（`executeUpdate`）按语句类型分发：

| 类型 | 流程 |
| --- | --- |
| INSERT | 构建 Row → 生成 rowKey → 转 KeyValue → 路由到 RS → PutRequest |
| DELETE | 尝试单行删除（主键等值）→ 失败则先 SELECT 匹配行再批量删除 |
| UPDATE | 禁止更新主键列 → 获取匹配行 → 应用赋值 → 批量 PutRequest |
| CREATE TABLE | 向 Master 发送 CreateTableRequest |
| DROP TABLE | 向 Master 发送 DeleteTableRequest |

写重试逻辑：
+ `executeTypedPutMutation` 在路由过期错误时重试一次
+ `fetchExistingRowWithRetry` 在行未找到时重试一次（路由缓存可能在分裂/迁移后过期）

SQL 指标上报：异步向 Master 报告 SQL 执行指标（类型、表名、延迟、成功/错误）。

### 4.3 MiniSQLStatement
基础 JDBC `Statement` 实现。`execute(sql)` 通过检查 SQL 前缀自动判断是查询还是更新。支持 `addBatch`/`executeBatch` 顺序批量执行。

### 4.4 MiniSQLPreparedStatement
JDBC `PreparedStatement` 实现。存储参数化 SQL 和参数 Map。`buildSql()` 遍历 SQL 替换 `?` 占位符：字符串用单引号包裹（`''` 转义），数字直接转字符串，布尔值转为 `1`/`0`。

### 4.5 MiniSQLResultSet
JDBC `ResultSet` 实现。内存中、只向前、只读的游标。支持 `next()`、`getString()`、`getInt()`、`getLong()`、`getDouble()` 等取值方法。导航方法（`first()`、`last()`、`previous()`）均已实现。包含副本读取警告（SQLWarning）。

### 4.6 MiniSQLResultSetMetaData
JDBC `ResultSetMetaData` 实现。将 MiniSQL 类型名映射到 `java.sql.Types` 常量。精度/小数位数使用硬编码默认值（如 INTEGER precision=10，VARCHAR precision=255）。

## 5. 路由系统

### Router
将 table + rowKey 映射到正确的 RegionServer。以 ZooKeeper 为路由数据的唯一真相来源，结合本地缓存和双机制失效。

缓存失效双机制：
1. **TTL**：30 秒过期（基于 `System.nanoTime()`）
2. **ZK Watcher**：三级监听
   + 表级：监听 `/minisql/tables/{table}/regions` 子节点变化
   + Region 级：监听每个 Region 的子节点变化
   + 节点级：监听 `primary` 和 `replicas` 数据节点变化

Watcher 触发时移除对应表的缓存条目并刷新。

路由算法：`route(tableName, rowKey)` 调用 `getOrRefreshRegions()` 获取有序 Region 列表，`findRegionByKey()` 在按 startKey 排序的列表上执行二分查找，找到 startKey <= rowKey 且 rowKey < endKey 的 Region。

缓存刷新流程：读取 ZK 子节点获取 RegionId 列表 → 解析每个 Region 的元数据（regionId|tableName|startKey(Base64)|endKey(Base64)）→ 读取 primary 和 replicas 节点 → 按 startKey 排序后缓存为不可变列表。

## 6. 分布式查询执行引擎

### 6.1 ParallelQueryExecutor
分布式查询执行的顶层门面。分析 AST 并委托到专门的执行器。

查询执行流程：

1. **分析**：判断是否有 JOIN、聚合、WHERE、ORDER BY、LIMIT
2. **WHERE 下推**：所有 WHERE 条件都通过 `ConditionSerializer.toSql()` 序列化为 SQL 字符串发给 RegionServer，由 RS 端的 `PredicatePushdownPlanner` 决定哪些条件可以在存储层执行，剩余条件由 RS 做行级过滤
3. **列投影**：`QueryPlanner` 计算需要从服务端获取的列（SELECT、WHERE、ORDER BY、GROUP BY、聚合中引用的列）
4. **ORDER BY/LIMIT 下推**：无 JOIN 且无聚合时，直接推到 RegionServer

三种执行路径：

| 路径 | 条件 | 执行器 |
| --- | --- | --- |
| 两阶段聚合 | 聚合可下推 | `AggregationExecutor.fetchAggregatedRows()` → 客户端合并 |
| JOIN | 存在 JOIN | `JoinExecutor.execute()` |
| 简单扫描 | 其他 | `ScanExecutor.fetchSourceRows()` → 本地算子管道 |

### 6.2 ScanExecutor
并行扫描多个 Region 的数据，支持 Region 裁剪和副本容错读取。

Region 裁剪流程：
1. 通过 `ScanRangeAnalyzer` 从 WHERE 条件和表 schema 中提取主键扫描范围（lowerBound, upperBound）
2. 将扫描范围与 Router 中每个 Region 的 startKey/endKey 做交集判断
3. 只向有交集的 Region 发送扫描请求，跳过无关 Region
4. 无法提取范围时退化为全量扫描

扫描范围提取（`ScanRangeAnalyzer`）：
+ 仅处理单主键列上的等值和范围条件（=, >, >=, <, <=）及 AND 组合
+ 值通过 `RowKeySerializer` 序列化为保序字节，与 Region 边界直接比较
+ AND 条件通过 `intersect()` 取交集（startKey 取 max，endKey 取 min）
+ OR 条件、复合主键、非主键条件等无法提取范围，返回 `fullScan`

并行扫描流程：
1. 确定目标 Region（有 rowKey 时路由到单个 Region，否则通过 Region 裁剪筛选）
2. 每个 Region 提交一个 `Callable` 到线程池
3. 每个 Callable 优先读 Primary；Primary 不可用时（UNAVAILABLE/DEADLINE_EXCEEDED）按序回退到副本
4. 等待所有 Future 完成（带超时）
5. 合并所有结果

副本回退时会记录警告信息到 `replicaReadWarnings`，最终附加到 ResultSet 的 SQLWarning 中。

### 6.3 AggregationExecutor
实现两阶段分布式聚合。

第一阶段（Region 端）：并行向每个 Region 发送包含 `AggregateSpec`（函数、列、输出名）和 `groupByColumns` 的 `ScanRequest`。RegionServer 返回 `AggregateGroup` 包含部分 SUM、COUNT、MIN、MAX。

第二阶段（客户端合并）：按 group-by key + 输出名聚合：
+ SUM：跨 Region 累加
+ COUNT：跨 Region 累加
+ AVG：最终 `SUM / COUNT`
+ MIN/MAX：跨 Region 字符串比较取极值

### 6.4 JoinExecutor
处理跨表和跨 Region 的 JOIN 查询。

JOIN 执行流程：
1. 使用 `ConditionSplitter` 将 WHERE 拆分为左表条件、右表条件和跨表条件
2. 分别序列化左右表条件为 SQL 字符串，下推到对应的 RegionServer
3. 分别获取左表和右表数据
4. 注册带表名前缀的限定列名（`users.id` 和 `id`），使 JoinOperator 能匹配不同表的列
5. 从 ON 子句提取等值连接条件；RIGHT JOIN 通过交换左右源转为 LEFT JOIN
6. 后续管道：跨表 WHERE 过滤 → 可选聚合 → ORDER BY/LIMIT/Projection

### 6.5 QueryPlanner
纯 AST 分析工具（无 I/O），计算列投影和提取查询元数据。

主要函数：
+ `determineProjectedQualifiers()` — 单表查询：收集 SELECT、ORDER BY、WHERE 中引用的列名，去除表名前缀
+ `determineJoinProjectedQualifiers()` — JOIN 的一侧：按表名/别名过滤引用列
+ `extractJoinConditionColumns()` — 从 ON 条件提取等值连接列对

### 6.6 ConditionSerializer
将 AST 条件树转回 SQL WHERE 子句字符串用于服务端谓词下推。

所有 WHERE 条件都尝试下推到 RegionServer，不做客户端侧的可下推性判断。由 RS 端的 `PredicatePushdownPlanner` 根据表结构和存储引擎能力决定实际下推策略，无法在存储层执行的条件由 RS 做行级过滤。

序列化（`toSql`）支持的 AST 节点：
+ `SimpleCondition` → `column op 'value'`
+ `BetweenCondition` → `column [NOT] BETWEEN 'low' AND 'high'`
+ `InCondition` → `column [NOT] IN ('v1', 'v2', ...)`
+ `IsNullCondition` → `column IS [NOT] NULL`
+ `NotCondition` → `NOT inner`
+ `CompoundCondition` → `(left OP right)`

### 6.7 PipelineAssembler
组装 Volcano 风格的算子管道。

主要操作：
+ `appendAggregate()` — 包装 `AggregateOperator`（含 GROUP BY），可选追加 `FilterOperator` 用于 HAVING
+ `appendOrderByLimitProject()` — 链式组装 SortOperator → ProjectOperator（支持别名）→ DistinctOperator（SELECT DISTINCT）→ LimitOperator
+ `drain()` — 执行管道：`open()` → `nextRow()` 循环 → `close()`

## 7. 命令行客户端

### 7.1 SqlCli
交互式 SQL 命令行客户端。

启动参数：`--host <zkHost>`（默认 localhost）、`--port <zkPort>`（默认 2181）。

启动流程：注册 Driver → 构建 URL → 获取 Connection → 进入 read-eval-print 循环。

多行支持：行不以 `;` 结尾时进入多行模式（提示符变为 `->`），累积输入直到遇到 `;`。

特殊命令（无需分号）：`help`、`exit`/`quit`、`source <file>`（从文件读取执行 SQL）、`describe <table>`/`desc <table>`、`show tables`。

### 7.2 CliResultFormatter
格式化 JDBC ResultSet 为 ASCII 表格。两遍扫描：第一遍读取所有行并计算列宽（上限 50 字符），输出包含分隔线、表头、数据行和行数统计。长值截断显示 `...`，NULL 显示为 "NULL"。
